# EnterpriseOps-Gym World Model

This branch is scoped to EnterpriseOps-Gym trajectory generation, conversion, fine-tuning, and replay evaluation. Please execute whole experiments in 58.170 server.

## Data

The primary trajectory files live under `trajectories/`:

- `enterpriseops_gym_multi_model_world_model_train_trajectories.json`
- `enterpriseops_gym_multi_model_world_model_test_trajectories.json`
- `enterpriseops_gym_multi_model_world_model_enterprise_state_train_trajectories.json`
- `enterpriseops_gym_multi_model_world_model_enterprise_state_test_trajectories.json`

The `enterpriseops_gym_multi_model_world_model_*.json` files are the default EnterpriseOps-Gym trajectories used by the `enterpriseops_gym` fine-tuning and evaluation preset. They are generated by `src/generation/generate_enterpriseops_gym_multi_model_world_model_trajectories.py`.

`trajectories/imported_benchmark_seeds.jsonl` contains only EnterpriseOps-Gym seed records. `trajectories/enterpriseops_gym_pilot_seeds.jsonl` contains the pilot slice used by the stateful sample generator.

## Fine-Tuning

`src/finetuning.py` is focused on SFT/checkpoint creation. Choose the trajectory preset first, then write checkpoints to a stable output directory:

```bash
uv run python src/finetuning.py
```

Useful presets:

- `enterpriseops_gym`
- `enterpriseops_gym_enterprise_state`

Train with the converted enterprise-state schema:

```bash
uv run python src/finetuning.py \
  --trajectory-dataset enterpriseops_gym_enterprise_state \
  --use-lora \
  --bf16 \
  --gradient-checkpointing \
  --output-dir checkpoints/gymops_enterprise_state
```

Train with the default EnterpriseOps-Gym trajectory schema:

```bash
uv run python src/finetuning.py \
  --trajectory-dataset enterpriseops_gym \
  --use-lora \
  --bf16 \
  --gradient-checkpointing \
  --output-dir checkpoints/gymops_world_model
```

Use `--resume-from-checkpoint /path/to/checkpoint` to continue an interrupted run. The value passed to `--output-dir` is the directory to pass to `src/evaluation.py --world-model-path` after training completes. If the trainer creates numbered checkpoint subdirectories and you want a specific step, pass that checkpoint directory instead.

## Evaluation

First, generate the task configs by the command:

```bash
uv run python src/enterpriseops_gym/dump_enterpriseops_gym_task_configs.py \
  --domain csm itsm teams email drive calendar hr hybrid \
  --output-dir trajectories/enterpriseops_gym_task_configs
```

`src/evaluation.py` owns next-state prediction evaluation and EnterpriseOps-Gym agent replay. It imports the official gym package from the workspace-local `EnterpriseOps-Gym/` directory by default:

```bash
uv run python src/evaluation.py \
  --world-model-path checkpoints/gymops_enterprise_state \
  --gym-task-configs trajectories/enterpriseops_gym_task_configs
```

Use `--skip-next-state-eval` or `--skip-agent-replay` to run only one evaluation path.

There are two ways to load the world model for evaluation:

1. vLLM-based server: start a vLLM server with a served model name, then pass the matching vLLM method name to `src/evaluation.py --world-model-method`. If the server is not on port 9000, pass `--vllm-server-port`. For the example below, the served model name is `gymops_world_model` and the evaluation argument is `--world-model-method vllm/gymops_world_model`. This is recommended for faster inference.
2. Direct checkpoint loading: pass a local checkpoint or output directory to `src/evaluation.py --world-model-path`.

The following command launches a vLLM server with the served model name `gymops_world_model`:

```bash
vllm serve Qwen/Qwen3.6-27B-FP8 \
  --enable-lora \
  --lora-modules gymops_world_model=sessions/gymops_binary_new/checkpoint-6900 \
  --tensor-parallel-size 1 \
  --max-model-len 200000 \
  --port 9000 \
  --host 0.0.0.0 \
  --reasoning-parser qwen3 \
  --language-model-only \
  --default-chat-template-kwargs '{"enable_thinking": false}' \
  --served-model-name gymops_world_model \
  --kv-cache-dtype fp8 \
  --gpu-memory-utilization 0.92 \
  --enable-prefix-caching \
  --enable-chunked-prefill \
  --max-num-seqs 256 \
  --max-num-batched-tokens 8192
```

### LlamaFactory `canonical_event_with_nudge` next-state evaluation

`src/analysis/evaluate_llama_factory_canonical_event.py` scores a LlamaFactory-trained
world model on the `canonical_event_with_nudge` next-state prediction task. It reads the
alpaca eval files produced by
`src/data_preparation/convert_canonical_nudge_to_llama_factory.py`
(`data/llama_factory/canonical_event_with_nudge/*eval.json`), replays each `{instruction,
input}` as the system/user chat turns, parses the model's JSON, and scores every categorical
field against the gold `canonical_event_with_nudge` label using the same match logic as
`src/evaluation.py`. Per-benchmark and overall micro/macro field accuracy, `full_match_rate`,
and per-field accuracy are printed and written to `--output`
(default `data/evaluation/llama_factory_canonical_event_eval_results.json`); the
`canonical_field_comparisons` records are drop-in compatible with
`src/analysis/calculate_canonical_field_accuracy.py`.

Recommended: score against a running vLLM server (fast, batched). Start the server with the
LoRA checkpoint served as `gymops_world_model`:

```bash
vllm serve Qwen/Qwen3.6-27B-FP8 \
  --enable-lora \
  --lora-modules gymops_world_model=/path/to/ckpt/ \
  --tensor-parallel-size 1 \
  --max-model-len 65536 \
  --port 9010 \
  --host 0.0.0.0 \
  --reasoning-parser qwen3 \
  --language-model-only \
  --default-chat-template-kwargs '{"enable_thinking": false}' \
  --served-model-name gymops_world_model \
  --kv-cache-dtype fp8 \
  --gpu-memory-utilization 0.92 \
  --enable-prefix-caching \
  --enable-chunked-prefill \
  --max-num-seqs 256 \
  --max-num-batched-tokens 8192
```

Then run the evaluation against it (`--concurrency` issues parallel requests to exploit the
server's batching; `--limit 0` scores every example in each eval file):

```bash
uv run python src/analysis/evaluate_llama_factory_canonical_event.py \
  --vllm-base-url http://localhost:9010/v1 \
  --vllm-model gymops_world_model \
  --limit 0 \
  --concurrency 64 \
  --output data/evaluation/llama_factory_canonical_event_eval_results.json
```

Alternatively, load a checkpoint directly (a merged HF causal LM, or a LoRA adapter directory
with `adapter_config.json`) as the first positional argument. This path generates one example
at a time and is much slower, so `--limit` defaults to 200 examples per eval file:

```bash
uv run python src/analysis/evaluate_llama_factory_canonical_event.py \
  sessions/all_canonical_nudge/checkpoint-13755/ \
  --limit 200
```

## `react_wm` family of replay modes

In addition to the original `baseline` / `revision` / `imagined` replay modes,
this repo provides three new replay modes — the **`react_wm` family** —
runnable from the same `src/evaluation.py` entrypoint via `--agent-replay-mode`.
These were integrated from a separate state-design/model-training experiments
repository and adapted to reuse this repo's existing trajectory format,
world-model API, and agent-generator factory.

| Mode | What it does | How K (foresight depth) is chosen |
|------|--------------|------------------------------------|
| `react_wm` | Standard ReAct, plus a `[World-model foresight] ... [End foresight]` user message injected before each agent turn (after turn 0) with a K-step rollout of the world model. | Fixed via `--react-wm-k` |
| `react_wm_decide_k` | Same as `react_wm`, but the action policy itself decides K via a one-shot prompt each turn. K is clipped to `[0, --react-wm-kmax]`. | Agent-prompted (one extra LLM call per turn) |
| `react_wm_rl_k` | Same as `react_wm`, but a separately trained **K-controller** (a small local LM with a K-head) picks K per turn. The action policy is unchanged. | RL-trained K-head — one local forward pass per turn |

All three modes use the **same world model** (selected via `--world-model-method` or `--world-model-path`) and the **same action policy** (selected via `--agent-model` or `--llm-config`). They differ only in how the foresight depth K is selected at each turn.

**Foresight search strategy.** By default the K-step foresight is a single greedy rollout (one action proposed per imagined step). Passing `--imagined-trajectory-selection-strategy topk_search` switches the foresight to a **beam search** of depth K: at each imagined step the policy proposes `--imagined-trajectory-candidate-actions` candidate actions, each is scored (world-model success + stage progression, repeated-action penalty), and the `--imagined-trajectory-top-k` highest-scoring partial trajectories are retained. The single best beam is rendered into the `[World-model foresight] ... [End foresight]` message. This reuses the same scoring/pruning machinery as the `imagined` mode's `topk_search`, so it composes with any of the three K-selection mechanisms (e.g. `react_wm_rl_k` + beam search). With the default `--imagined-trajectory-selection-strategy llm_judge` the `react_wm` foresight stays a single greedy rollout and these knobs are ignored.

The `--world-model-target` flag picks which state design the world model predicts (and the K-controller was trained against): `tool_execution_result_binary` (binary success/failure, with optional `--include-error-message-in-target`), `state` (structured JSON state), or `tool_output` (raw tool output text).

All new code lives under `src/itp/` so the original ewm pipeline is unaffected:

- `src/itp/react_wm.py` — per-turn world-model foresight builder and the `[World-model foresight] ... [End foresight]` chat envelope shared by all three modes.
- `src/itp/k_decider.py` — one-shot prompt-based K decider used by `react_wm_decide_k`.
- `src/itp/k_controller.py` — runtime `KController` that loads the K-controller checkpoint and predicts K per turn.
- `src/itp/training/train_adaptive_k.py` — two-stage K-controller trainer (offline-RL pseudo-labelling + supervised K-head training); reuses ewm's trajectory format and world-model API.

### Evaluation options

`src/evaluation.py --agent-replay-mode` accepts both single-mode values and three shortcut values:

| `--agent-replay-mode` value | Runs | When to use |
|---|---|---|
| `baseline`, `revision`, `imagined`, `react_wm`, `react_wm_decide_k`, `react_wm_rl_k` | One mode | Granular runs / per-mode output dirs. Easy to retry individual modes. |
| `all` (default) | baseline + revision + imagined (the three original modes) | Reproduce the original ewm comparison. |
| `itp_only` | react_wm + react_wm_decide_k + react_wm_rl_k (the three new modes) | Compare the new modes head-to-head. Requires `--k-controller-path`. |
| `all_with_itp` | all six modes in one run | Full head-to-head: originals vs. `react_wm` family. Requires `--k-controller-path`. |

### Training the K-controller for `react_wm_rl_k`

`react_wm_rl_k` uses **reinforcement learning to optimize K**: a separately trained K-controller (a small local LM with a K-head on top of a `<CTRL>` token) predicts the best foresight depth per turn, while the action policy (e.g. GPT-5.1) remains in charge of tool selection.

The training pipeline has two stages:

- **Stage I — `label` (offline-RL pseudo-labelling).** For each expert `(state, action)` step in the training trajectories, score every candidate K with the reward
  ```
  R(K) = logprob( action  |  state, K-step foresight )  −  λ_k · K
  ```
  where the foresight is produced by the trained world model and the logprob is computed under the small policy LM. The `−λ_k · K` term penalises foresight depth, so the pseudo-optimal label `K* = argmax_K R(K)` is the **cheapest depth that still helps the policy reproduce the expert's action**. `λ_k` (`--lambda-k`, default `0.2`) is the foresight-cost knob.
- **Stage II — `sft` (joint supervised training).** SFT the small policy LM with a `<CTRL>`-positioned K-head on the labelled JSONL. Joint loss = action LM loss + `β_k · CE(k_head_logits, K*)`. After Stage II, the K-head predicts K* directly from the state alone — no world-model rollout needed at inference time.

Stage III (online A2C) is intentionally not included because the action policy at deployment time is typically an external API (e.g. GPT-5.1) that cannot sit inside the inner training loop.

```bash
TRAIN_TRAJECTORIES=trajectories/enterpriseops_gym_multi_model_world_model_train_trajectories.json \
WORLD_MODEL_TARGET=tool_execution_result_binary \
INCLUDE_ERROR_MESSAGE_IN_TARGET=1 \
WM_METHOD=vllm/gymops_world_model \
OUT_DIR=sessions/k_controller_binary \
KMAX=3 LAMBDA_K=0.2 \
bash scripts/run_k_controller_training.sh
```

This writes:
- `sessions/k_controller_binary/labeled.jsonl` (Stage I output — per-step pseudo-K labels)
- `sessions/k_controller_binary/policy_sft_khead/` (Stage II checkpoint — pass this directory to `--k-controller-path`)

### Evaluating `react_wm_rl_k` (RL-trained K-controller)

At inference time the K-controller runs one forward pass per turn on the runtime state text and the orchestrator uses `K = argmax(k_head)` (or sampled K, with `--k-controller-do-sample`) to decide how many steps the world model rolls forward before the next agent call.

```bash
uv run python src/evaluation.py \
  --trajectory-dataset enterpriseops_gym \
  --world-model-method vllm/gymops_world_model \
  --world-model-target tool_execution_result_binary \
  --include-error-message-in-target \
  --agent-replay-mode react_wm_rl_k \
  --react-wm-kmax 3 \
  --k-controller-path sessions/k_controller_binary/policy_sft_khead \
  --gym-task-configs trajectories/enterpriseops_gym_task_configs \
  --output-dir results/evaluation/react_wm_rl_k \
  --agent-model gpt5.1
```

`--react-wm-kmax` upper-bounds the K-head's output and must be ≤ the `kmax` recorded inside the checkpoint. The K-controller's saved kmax always wins if they disagree.

### Using Azure OpenAI instead of OpenAI

The agent model factory (`src/evaluation.py: build_agent_generator`) supports
three styles of Azure OpenAI endpoint via `--agent-model azureopenai/<deployment>`:

| Endpoint style | Example | Notes |
|---|---|---|
| Standard Azure resource | `https://<resource>.openai.azure.com` | SDK auto-builds `/openai/deployments/{deployment}/chat/completions`. |
| OpenAI-compatible (Azure v1) | `https://<resource>.openai.azure.com/openai/v1` | Routed through `openai.OpenAI(base_url=...)`. |
| Direct base URL (vendor proxy where the deployment is baked into the URL path) | `https://api.<vendor>.com/.../gpt-5.1` | Auto-detected by `--llm-config` (sets `AZURE_OPENAI_DEPLOYMENT_IN_URL=1`), or set that env var yourself. |

#### Option A — load credentials from a JSON file (recommended; no `export` needed)

Keep your credentials in a JSON file outside the repo (e.g. `~/llm-config.json`)
and pass `--llm-config ~/llm-config.json`. The file uses these fields:

```json
{
  "llm_provider":     "azureopenai",
  "llm_model":        "gpt-5.1",
  "llm_api_key":      "<your-key>",
  "llm_api_endpoint": "https://<your-gateway>/chat/gpt-5.1",
  "llm_api_version":  "2025-04-01-preview",
  "temperature":      0.1,
  "max_tokens":       16384
}
```

The loader (`_apply_llm_config_file` in `src/evaluation.py`) maps:

- `llm_api_key` → `AZURE_OPENAI_API_KEY`
- `llm_api_endpoint` → `AZURE_OPENAI_ENDPOINT`
- `llm_api_version` → `AZURE_OPENAI_API_VERSION`
- Auto-sets `AZURE_OPENAI_DEPLOYMENT_IN_URL=1` when the endpoint is *not* a
  standard `*.openai.azure.com` resource URL or `/openai/v1` compat URL.
- Auto-sets `--agent-model` to `azureopenai/<llm_model>` when `--agent-model`
  was not passed explicitly.
- `temperature` and `max_tokens` are read but currently ignored (the script
  controls these via its own knobs / `--max-new-tokens`).
- `llm_provider` may also be `openai` (sets `OPENAI_API_KEY` /
  `OPENAI_BASE_URL`) or `gemini` (sets `GEMINI_API_KEY` /
  `GEMINI_API_BASE_URL`).
- Existing env vars are **never overwritten** by the JSON file.

Smoke-test run with this single flag:

```bash
uv run python src/evaluation.py \
  --llm-config ~/llm-config.json \
  --skip-next-state-eval \
  --agent-replay-mode react_wm --react-wm-k 2 \
  --world-model-path /data/.../gymops_world_model \
  --world-model-target tool_execution_result_success_failure \
  --include-error-message-in-target \
  --gym-task-configs trajectories/enterpriseops_gym_task_configs \
  --max-agent-tasks 2 \
  --output-dir results/evaluation/react_wm_smoke
```

`--agent-model` is filled in automatically from the JSON (`azureopenai/gpt-5.1`).
`--skip-next-state-eval` is recommended for Azure-only setups because the
offline next-state LLM judges in `evaluate_world_model_predictions` hit OpenAI
directly with `gpt-4o`. The agent replay (where `react_wm*` runs) does not
need those judges.

#### Option B — set the env vars yourself

```bash

export AZURE_OPENAI_ENDPOINT="https://api.example.com/path/to/gpt-5.1"
export AZURE_OPENAI_API_VERSION="2025-04-01-preview"
export AZURE_OPENAI_DEPLOYMENT_IN_URL=1

```
